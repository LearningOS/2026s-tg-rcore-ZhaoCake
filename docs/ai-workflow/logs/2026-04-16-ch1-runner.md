# ch1 运行链路理解日志

## 目标与上下文

- 目标：理解为什么 `cargo run` 会直接显示并执行 QEMU 命令。
- 背景：我在 `tg-rcore-tutorial-ch1` 中执行 `cargo run`，终端显示：
  - `Running qemu-system-riscv64 ... -kernel ...`
  - 并输出 `Hello, world!`
- 疑问：`test.sh` 里只有 `cargo run`，为什么没有手写 qemu 命令却能启动模拟器？

## 关键定位过程

1. 查看 `test.sh`
- 结论：脚本只是调用 `cargo run` 并检查输出是否包含 `Hello, world!`。

2. 查看 `.cargo/config.toml`
- 结论：`[target.riscv64gc-unknown-none-elf]` 下配置了 `runner`，即 qemu 启动参数。
- 这意味着：只要是该 target，`cargo run` 会自动把产物交给 runner，而不是在宿主机直接执行。

3. 查看 `build.rs`
- 结论：`build.rs` 负责生成链接脚本和内存布局，不负责运行命令。

## 最终理解

- `cargo run` 的行为由 Cargo 配置决定。
- ch1 的运行链路是：
  - `test.sh` -> `cargo run`
  - Cargo 读取 `.cargo/config.toml` 的 `build.target` 与 `target.<triple>.runner`
  - Cargo 在编译完成后调用 qemu runner，并把 ELF 产物路径追加到 `-kernel`

## 为什么这仍然是 bare-metal

- bare-metal 指目标程序运行时不依赖宿主机操作系统服务。
- 由于目标是 RISC-V 裸机 ELF，宿主机不能直接执行，所以开发阶段借助 QEMU 作为“运行器”。
- 因此“裸机程序 + 模拟器运行”并不矛盾。

## 本次收获

- 以后排查“`cargo run` 到底执行了什么”时，优先看：
  - `.cargo/config.toml` 的 `build.target`
  - `.cargo/config.toml` 的 `runner`
  - `Cargo.toml` 与 `build.rs`（分别看依赖和链接/构建逻辑）
